    一个 AI 的书房
    是怎样建成的

    pi-knowledge 是一个本地优先的 RAG 知识库插件。它把你散落在仓库里的代码、文档、PDF、网页， 做成一座可以按「意思」或「原词」随时查的私人图书馆——让编码智能体在每次新会话里， 都能从你的真实项目出发回答，而不是靠猜。

    从全景图开始 直接看关键数字

    先看问题：AI 为什么记不住你的项目

    编码智能体并不笨，它只是每次打开工位时，桌上都是空的。

    想象一位能力很强的新同事：读代码飞快、写代码也快，但有个奇怪的毛病—— 每天上班都会失忆。昨天你们一起理清的登录流程、上周定下的目录约定、 三个月前写进 README 的部署细节，今天他全都不记得。

    这就是编码智能体的默认状态。它每次会话只拥有两样东西： 当前上下文窗口里能放下的内容，以及它能主动去读的文件。 而真实项目往往有几千个文件、几十万字文档，还有散落在 PDF、网页、会议记录里的知识。 把整个项目塞进提示词，既贵又慢，而且一定会超出窗口。

    先说人话

    这就像让一个博学的顾问回答你公司的问题，但不给他任何资料，只允许他"凭印象说"。 RAG（检索增强生成）做的事很朴素：先帮顾问建一个图书馆， 他回答前先去查资料，查到了再开口。

    pi-knowledge 的定位需要和另一类插件区分开： pi-memory 管理的是智能体自己写的笔记； pi-knowledge 索引的是你已经存在的文件。 前者像便签本，后者像档案馆。

    RAG 的三个动作

    README 引用了 Lewis 等人 2020 年的 RAG 论文。落到工程上，它只有三个动作， 而 pi-knowledge 的绝大多数复杂度都花在把这三个动作做稳：

    1. 离线建索引：把原始资料切成小块，转成机器能比较的表示，存起来。
    2. 在线检索：用户提问时，从索引里找出最相关的几块。
    3. 只注入相关上下文：把这几块交给模型，而不是整个代码库。
    一个关键区别：检索系统不"理解"你的项目，它只负责把最可能相关的那几页翻出来。 答案是否正确，仍取决于模型如何使用这些材料。所以"检索质量"和"回答质量"是两件事， pi-knowledge 的工程重心明显押在前者。

    全景：一个插件，两个房间

    一边是"建馆"——把文件变成可检索的数据；一边是"找书"——把问题变成带出处的答案。 中间隔着三份账本。

    先说人话

    这个插件把自己挂成 Pi 的扩展：安装后，智能体多了 13 个"图书管理员工具"， 并且在每轮对话开始前，系统会告诉它"你有哪些知识库可用"。 真正的重活在你显式让它建库/搜索时发生，平时它几乎不占资源。

    启动为什么这么轻

    这是整个项目最值得先讲的一个工程决定。Pi 在安装插件时会先"检查"一遍扩展入口； 如果入口文件顶层就 import 了 SQLite 原生模块或 ONNX 运行时，安装校验就会被迫加载这些重依赖， 在跨平台环境里极易失败。

    所以它做了三层延迟：

    • extension.js 只有 12 行，只负责把 dist/index.js 转发出去；
    • dist/index.js 顶层零静态 import，连参数校验的 JSON Schema 都是自己内联实现的；
    • 引擎、SQLite、文件监听、模型客户端，全部在第一次真正用到时才 await import()。
    再看实现

    扩展注册了 4 类钩子：session_start 初始化引擎、按需启动文件监听； before_agent_start 把知识库清单追加进系统提示； context 在开启自动注入时，用最后一次用户消息做一次 fast 检索，把前 3 条结果前置成一条 [Knowledge context] 消息； session_shutdown 收尾。

    模块级开关 PI_KNOWLEDGE_WATCH 和 PI_KNOWLEDGE_AUTO_INJECT 都是 opt-in，而且在模块加载时读取一次——会话中途改环境变量不会生效。 这是一个刻意的取舍：把"每轮自动检索"留成用户显式开启的能力，避免默认行为悄悄变贵。

    建馆：把一堆文件变成可检索的知识

    索引管线做六件事：扫描、切块、加前缀、算向量、落库、记账。 难点不在“做”，而在“遇到脏数据、大文件、超长段落、中断崩溃时还能做对”。

    先决定“索引谁”，再决定“怎么切”

    一个真实项目的目录里，大部分文件对检索没有价值：依赖包、构建产物、压缩的二进制、锁定文件、密钥文件。 如果把这些全灌进去，不只是浪费算力和存储，更糟的是它们会稀释检索结果。

    所以扫描阶段先做三层过滤：

    1. 用户显式排除：exclude_paths 里列出的路径，整棵剪掉。
    2. 建议排除：约 40 条模式，包括 node_modules、dist、.env、*.pem、*secret*、压缩包、Playwright 缓存等。这些可以被用户确认后覆盖。
    3. 技术跳过：超过 10MB 的文件、二进制文件（读前 512 字节，发现 0x00 即判定）、不可读文件。无法绕过。
    先说人话

    它像一个负责任的搬家工人：默认不搬垃圾、不搬保险柜（密钥）、不搬超重家具（10MB 以上）， 但会先把“有多少东西、哪些没搬”列一张清单给你看——这就是 knowledge_plan。 你确认清单后，才真正开始花钱算向量。

    六种跳过原因。前三种是“建议排除”，后三种是“技术跳过”。
    原因触发条件能否覆盖典型例子
    suggested_excluded命中排除模式或 .gitignore可覆盖node_modules/、dist/、.env
    oversized文件大于 10 MiB不可打包后的 bundle.js
    binary前 512 字节含 0x00不可图片、可执行文件、压缩包
    unreadablestat/读取失败不可权限不足的文件
    inaccessible目录无法列出不可断开的挂载点
    extraction_failedPDF/DOCX 解析抛错不可损坏的文档
    一个容易忽略的边界：include_suggested_text: true 会连同 .gitignore 一起绕过—— 因为它和排除规则共用同一个 ignore 实例。想只纳入某几个被忽略的目录，更安全的做法是用 include_paths 精确指定。

    切块：三种刀法，一个共同目标

    为什么要切？两个原因： 模型一次只能处理有限长度的文本（本地 e5 是 512 token）； 检索需要“小而准”的单位——把整个文件当一个单位，命中后你只能拿到一大坨内容，既浪费上下文，也掩盖真正相关的那几行。

    pi-knowledge 没有用“固定字符数 + 重叠窗口”这种通用做法，而是按内容结构分三路：

    先说人话

    它不是在“按字数切纸”，而是在顺着内容天然的缝隙下刀： 文档顺着标题切，代码顺着函数和类切，实在没有结构才按段落切。 小函数会被打包成一捆，大函数会被拆到方法级，太长再按行切。

    再看实现

    Markdown：维护一个标题栈，遇到新标题先结束上一节；块的正文是 当前标题 + 空行 + 本节内容，元数据带 heading 与 breadcrumb。 同一节按 \n\n 拆段累加，超过 450 token 就先落一块。

    代码：用 tree-sitter 解析成语法树，识别函数、方法、类、接口、类型、变量等节点； 只有函数值（箭头函数、函数表达式）才会被当作可切单元，纯变量声明在 C/C++ 里会被跳过。 namespace 自身不产块，直接下钻。单块目标 900 token、硬上限 1,800； 同一父作用域下的小成员如果累计不超过 900 token，就合并成 symbol_kind: "group" 的块。 tree-sitter 给的是字节偏移，代码里专门建了 byte→UTF-16 索引映射，所以中文源码不会被切坏。

    没有重叠窗口：这是明确的取舍。省存储、省向量、避免同一段内容被重复召回； 跨块上下文交给检索期的 adaptive 模式在相邻块里补。

    为什么“再切一次”很重要：结构切块只能保证“语义上完整”，不能保证“模型吃得下”。 e5 的 tokenizer 只吃 512 token；早期版本用 truncation: true，超出部分被静默丢掉—— 结果是文件尾部的内容永远检索不到。0.12.0 改成先用 tokenizer 精确测量，再按结构边界二次切分， 并把策略版本写进 KB 元数据，旧库会被 knowledge_doctor 提示重建。

    每块内容都要办一张“身份证”

    假设两段代码都写着 return refresh(token)。一段在支付服务里，一段在登录服务里。 如果只把这段文字转成向量，它们会非常接近；但用户问“登录令牌怎么刷新”时，你只想要后者。

    解决办法不是让模型更聪明，而是在切片进入索引之前，把它的身份信息一起写进去。 这叫上下文检索（Contextual Retrieval）：Anthropic 的做法是让 LLM 给每块生成一段上下文说明； pi-knowledge 选择了一条更便宜、更保护隐私的本地路线——用文件路径、类型、标题面包屑、AST 结构拼出一个固定前缀。

    先说人话

    就像图书馆给每本书贴标签：书名、作者、分类、所在楼层。 读者找书时，标签和正文都能被搜索到——所以“RefreshToken 在哪个类里”这种问题才有可能被检索命中。

    再看实现

    前缀的拼接顺序是固定的：File、Type、Section（优先 breadcrumb）、 Language、Scope、Kind、Symbol、Signature，然后是空行和正文。 这份文本同时用于：

    • embedDocuments() 的输入（文档侧加 passage: 前缀）；
    • content_tokenized 字段，供 FTS5 建倒排索引；
    • 搜索时的 coverage 计算（查询词覆盖了多少信号词）。

    这也解释了为什么“搜文件名”能命中：文件名在 File: 行里，已经被分词进 FTS 了。 代价是通用词（比如 File、Type）会出现在每个块里，但 BM25 的 IDF 会自动压低它们的权重。

    把文字变成坐标：本地优先的向量化

    向量（embedding）是一串固定长度的数字。语义相近的文本，在这串数字构成的高维空间里距离更近。 “怎么重置密码”和“password reset procedure”字面完全不同，但向量可能很近——这就是语义检索的价值。

    默认本地模型e5-small多语言 · 384 维
    模型体积~32 MBONNX fp32，首次下载
    单块 token 上限512目标预算 448
    索引批量64可配置

    默认路径不需要 API key：模型跑在本地，首次使用时从 Hugging Face 下载到 ~/.pi/knowledge/models/，之后离线可用。如果想要更高精度，可以切到 OpenAI 兼容的嵌入 API （例如 text-embedding-3-small，或自建的 Qwen3-Embedding-8B）。

    先说人话

    本地模型像自带一台小型翻译机：不用联网、不花 API 费、代码不出门，代价是精度和速度不如云端大模型。 两种模式共用同一套存储格式，但向量空间不通用——换模型就必须重建索引。

    为什么模型要跑在独立子进程里？

    这不是洁癖，是被线上事故逼出来的。CHANGELOG 记录了几次严重问题： ONNX 运行时被加载进 Pi 的 TUI 进程后，macOS arm64 上退出会 abort； 宿主进程内做 ONNX dispose 会和空闲定时器竞争，出现 Session already disposed； OMP 的打包宿主甚至不是 Node，没有 child_process.fork().send()。

    于是有了现在的设计：model-worker.js 作为独立 Node 22+ 进程，客户端优先用 IPC， 宿主不支持 IPC 时自动退化到 stdio + JSONL（每行一个 JSON 请求/响应）。 worker 崩溃只会让当前批次失败，错误信息带上 stderr 尾部 4,000 字符；下次调用会自动重启。 宿主的 session_shutdown 只负责 SIGKILL worker，绝不在自己进程里做 ONNX 清理。

    向量空间是有“签名”的。每个 KB 记录模型名、维度、pooling、归一化、前缀策略，以及 API base URL 的短哈希。 签名对不上时，knowledge_search 会跳过该 KB 的向量召回并给出警告，但 BM25 仍可用。 换句话说：换模型不会悄悄给出错误答案，而是明确降级。

    落库：三份账本，各管一件事

    索引结果不是塞进一个大 JSON，而是拆成三份职责明确的存储： SQLite 管结构化元数据与全文索引，二进制文件管向量，模型目录管权重。

    先说人话

    SQLite 像图书馆的借阅目录：书名、位置、分类、摘要都在这。 向量文件像一柜按固定顺序摆放的“语义指纹卡”：第 3 张卡对应目录里第 3 本书， 所以中间抽走一本书，后面的卡片就全错位了——必须整柜重排。

    再看实现

    FTS5 使用外部内容表模式：正文存在 chunks 表，倒排索引存在 chunks_fts， 通过 3 个触发器（insert / delete / update）保持同步。入索引文本是预分词后的 content_tokenized：它把 camelCase 拆开（refreshToken → refresh Token）、 把 HTTPServer 拆成 HTTP Server、把字母和数字拆开，并给每个中文字符加空格， 这样配合 FTS5 默认的 unicode61 分词器，中文就能按字检索。

    向量文件只有 8 字节头 + 连续的 float32 矩阵，读的时候按 8 + i × dim × 4 定位。 写入先占位 8 字节，最后 close() 才回填真实的 count/dim，然后原子 rename。 半成品临时文件读出来是 count=0，天然不会被当成有效索引。

    找书：一次搜索要经过多少道关卡

    召回、融合、门槛、加分、去重、扩窗、重排。 每一道都只解决一个具体问题，而它们叠在一起，才让“搜索结果看起来像人找的”。

    两个馆员：一个记原词，一个懂意思

    检索系统最怕“只用一种找法”。只用关键词，会错过换个说法的内容；只用向量，会在一堆语义相近但事实上无关的块里翻车。 所以它同时雇了两个馆员：

    两种召回方式的强弱项。它们不是替代关系，而是互补关系。
    维度BM25（词法馆员）向量（语义馆员）
    怎么找FTS5 倒排索引，按词频、逆文档频率、长度归一化打分把查询和每块文本都变成向量，算方向相似度
    擅长精确符号、文件名、命令、错误码、配置键、引号短语概念、同义词、跨语言、描述性长问题
    盲区换个词就找不到；中文需要预分词“看起来像”但事实无关；低频专有名词不稳
    速度毫秒级，SQLite 内部完成需要一次查询嵌入 + 全库扫描（流式）
    可解释性能说清命中了哪些词只能说“向量近”，不易解释
    先说人话

    BM25 像图书馆的目录卡片：你报出准确书名或关键词，它立刻把书找出来。 向量像一位读过所有书的馆员：你说“那本讲怎么防止登录被劫持的”，他也能意会。 两个人都问一遍，再把答案合并，比单信一个人靠谱。

    再看实现

    BM25 用的是 SQLite FTS5 内置的 bm25()：默认 k1 = 1.2、b = 0.75，单列权重 1.0。 FTS5 返回的是负分（越相关越负），代码取反后才变成“越大越好”。 查询词会被包成短语并默认用 AND 连接；只有零结果且词数大于 1 时才退化成 OR。 fast 模式特意关掉了 OR 回退——它要的就是“精确”。

    向量侧先用 query: 前缀嵌入查询，然后按 rowid 顺序流式扫描整个 .bin 文件， 用一个长度等于 limit 的升序数组维护 top-K；只有入选的 K 条才复制向量，其余全部复用同一块 scratch 缓冲。 相似度函数名义上叫 cosine，实际只算点积——因为入库时已经做了 L2 归一化。

    融合：为什么不用 RRF

    两路召回的分数量纲完全不同：BM25 可能是 0 到 30 的任何值，向量相似度在 -1 到 1 之间。 合并前必须先归一化。pi-knowledge 用的是列表内 min-max 归一化 + 加权求和：

    fused(id) = 0.45 × norm(BM25) + 0.55 × norm(vector) + 0.15 × [两路都有] norm(x) = (x − min) / (max − min)；单元素列表归一为 1；理论上限 1.15，下限 0。

    RRF（倒数排名融合）是学术界的常用基线：只看名次，不看分数，鲁棒且无需归一化。 代码里确实还留着 reciprocalRankFusion()（k=60），但没有任何调用点。 原因写在 README 里：项目自己的实测发现，RRF 把分数压得太扁，导致排名诊断几乎不可用。 换成加权融合后，分数保留了“差多少”的信息，diagnostics 才能告诉你为什么某条排第一。

    一个实现细节：overlap 加成要求两路归一化分数都大于 0。 而每路列表的末名归一后恰好是 0，所以“只在两路都排最后”的块拿不到这 0.15。 这不是 bug，但说明分数不是概率，别拿它跨查询比较。

    置信门：宁可不答，也不硬凑

    语义检索最危险的失败模式不是“没找到”，而是找到了一堆看起来很像、实际上无关的内容。 模型拿到这些内容，会非常自信地编出一个错误答案。

    所以 hybrid 路径设了一道门：候选必须同时满足分数阈值和词法证据。

    score ≥ 0.18　（balanced profile）
    且 hasEnoughLexicalEvidence：
    　n ≤ 1　　　　　→ 直接通过
    　sourceFileBoost ≥ 0.22 → 直接通过（文件名/路径已是强证据）
    　n ≤ 3　　　　　→ coverage ≥ 1/n
    　其他　　　　　→ coverage ≥ 0.34 n = 查询中的信号词数量；coverage = 命中信号词 / 全部信号词。阈值随 profile 变化：precision 0.4，recall 0.12。

    这套规则的精妙之处在于它不是一刀切：短查询（1 个词）只要命中就放行； 中等查询命中一个词也算过；长查询才要求 34% 的覆盖率。 同时，文件名或路径的强命中可以直接绕过覆盖率要求——因为“你搜的文件名就在路径里”几乎不会是假阳性。

    注意门槛用的是“加过 boost 的分数”，不是原始融合分。 路径、文件名、文档位置带来的加成会实打实提高通过率。 这意味着一个纯 BM25 命中（原始分可能只有 0.2 多）的代码文件，很容易过 0.18 的线； 而一个语义上很像、但没有任何词法交集的块，会被稳稳地挡在外面。

    加分与惩罚：让“该出现的”排在前面

    融合分只回答“相关性”，不回答“哪个更像用户要的”。于是排序阶段又叠了一层业务规则：

    排序阶段的加减分规则（balanced profile 基准）
    规则条件效果为什么
    路径命中查询词出现在文件路径里+0.18 / 词，≤ +0.45路径本身就是强上下文
    文件名命中命中 basename（去掉扩展名与测试后缀）+0.32auth.ts 对“auth”查询几乎必中
    源码文件加成代码文件且命中路径≤ +0.22避免文档/生成物抢走代码查询
    文档加成安装/README/quickstart/docs+0.85 / +0.35“怎么装”这类问题文档优先
    测试惩罚测试文件，且查询不想找测试× 0.48测试代码通常不是实现答案
    反向测试惩罚非测试文件，但查询明确要测试× 0.88让测试文件相对上浮
    本地化惩罚locale/i18n/translations 下的文本× 0.20避免翻译文件淹没实现
    KB 信任系数stale / 目录 / 文本或 URL×0.92 / ×1.04 / ×0.98陈旧的库降权，本地文件优先

    这些规则有一个共同点：它们都不是“硬过滤”，而是“调分数”。 这意味着即使查询很奇特，相关结果也不会被彻底抹掉，只是排后面。

    去重与文件交错：不要让一个文件霸榜

    真实项目里有个固定现象：README 或某个大文件被切成几十块，每一块的向量都很像，于是一次搜索的前五条全是它。 用户看到的是“五段重复的话”，而不是五个答案。

    解决方案是 MMR（最大边际相关性）：每选一条，就把它和已选内容的“冗余度”算进去，下一轮优先选“相关性还行、但和已选不太重复”的。

    MMR(i) = λ × relevance(i) − (1 − λ) × redundancy(i)
    λ = 0.76（balanced）　/　0.62（strong）

    redundancy(i) = max over 已选 s of:
    　max( Jaccard(词集合), lineProximity(行距离), max(0, cos(向量)) × 0.35 ) 冗余度取三项中的最大值，不是加权和；向量项被压到最多 0.35，避免“向量像”一票否决。
    行邻近度（lineProximity）的阶梯。同一个 KB、同一个文件才开始计分。
    关系冗余度含义
    窗口有交集 / 行区间重叠1.0基本是同一段内容
    间隙 ≤ 20 行0.8极可能是上下游
    间隙 ≤ 80 行0.45同一小节
    同文件但更远0.2仍有一定冗余
    不同文件0不惩罚

    MMR 之后还有一道文件级交错：按文件分桶，然后轮转取号——第一轮每个文件取第 1 名，第二轮每个文件取第 2 名。 它可能把一条低分结果提到高分结果前面，这是故意的：对“我需要从多个文件里找线索”的场景，多样性比严格单调更有用。

    先说人话

    就像点菜：不让你把同一盘菜连点五份，而是每样先上一份。 真正需要“只看某一个文件”的场景，可以设 diversity: "off"，或者直接用 fast 模式。

    自适应扩窗：把“命中一行”变成“看得懂的上下文”

    切块是必要的，但它有个副作用：一个函数被切成一块，调用它的地方在另一块。 模型只拿到函数体，可能不知道它被谁调用、参数从哪来。

    adaptive 模式在检索后做一次“补上下文”：以命中的块为种子，从同一个文件里取出上下各 80 行的邻居， 按相关性和结构关系挑出最值得带的几块，按行号排序拼成一段连续文本。

    先说人话

    你问“这个函数怎么工作”，只给你函数体不够，还得给你它所在类、相邻的调用方。 adaptive 就是那个会顺手多翻两页的馆员——但它不会把整本书搬来，只挑最相关的几页。

    再看实现

    邻域选择有一个容易忽略的细节：先按分数选，再按行号排。 选择阶段用 score 降序，行号只做稳定 tie-break；拼装阶段重新按 start_line 排序， 保证输出是自然阅读顺序。若种子没被选进前 N，会被强制追加（Number.MAX_SAFE_INTEGER）。 最后按 maxContextChars 截断，允许最后一个块被切一半。

    它不是调用图分析：所有“兄弟/父子”判断都来自索引时写入的 AST 元数据，不分析真实的调用关系。 这也是它便宜、稳定的原因——不需要跑类型检查器或语言服务器。

    深度重排：请一位专家复核

    deep 模式在 hybrid 召回之后，取前 30 个候选，交给 cross-encoder 逐对打分： 把“查询 + 候选文本”一起送进模型，直接输出相关性分数。 它比向量检索慢得多，但判断更细，适合高风险问题或对答案做最终校验。

    默认本地模型是 Xenova/ms-marco-MiniLM-L-4-v2；也可以接 Cohere、Jina 或任意兼容 API（包括 Hugging Face 的 TEI）。 本地路径默认走 text-classification pipeline，输出经过 sigmoid，落在 0 到 1； 开 PI_KNOWLEDGE_RERANKER_RAW_LOGITS=true 可以拿原始 logit，避免强相关分数被压平。

    参数上的两个细节：重排最多取 limit × 3 条（balanced）； 送到重排器的单条文本默认截断到 12,000 字符，API 超时 30 秒。 重排器失败不会自动降级到本地——配置错了就直接报错，而不是给你一个“看起来正常”的结果。

    工程内功：让一场几小时的任务不把库弄坏

    算法决定“搜得好不好”，工程决定“能不能安心用”。 这一章讲那些不性感、但真正决定产品能不能活下来的细节。

    大项目：把长任务做成“可观察的状态”

    索引一个几万文件的项目，可能要跑几分钟到几十分钟。中途不能“看起来像卡死”， 也不能因为进程被杀就把整个库损毁。pi-knowledge 的做法是把长任务拆成可持久化的状态机：

    • 先规划再动手：目录扫描先只读元数据，算出可扫描文件数、字节数、跳过统计，再开始昂贵的嵌入。
    • 硬性分批：每 64 块嵌入一次；每 500 行分页读取 chunk；删除也按 500 一批。
    • 流式写盘：向量边算边追加到临时文件，不在内存里攒整个库。
    • 进度落库：indexing_jobs 表记录阶段、已处理文件/块数、跳过数、最后进度时间，ETL 细节全在 SQLite 里，换个会话也能查。
    • 卡死判定：status = indexing 且超过 10 分钟没有进度 → 判为 stuck，doctor 给 blocking 级告警。
    先说人话

    它把“搬家”做成了带物流单号的流程：搬了多少箱、哪箱没搬、现在卡在哪一步，都能查。 搬一半车坏了，它不会假装搬完了——库会停在“未完成”状态，检索不会去读它。

    增量更新：只重算真正变了的东西

    每次改几行代码就全量重建索引，是不现实的。pi-knowledge 的增量判定颗粒度是块，不是文件。 每个块有一个身份哈希：

    content_hash = sha256( file_path ␀ file_type ␀ start_line ␀ end_line ␀ metadata_json ␀ content ) 六个字段用 \0 连接。任何一项变化都会被视为“新块”。

    更新时，新切出的每个块去旧索引里找一个 hash 相同的“未被认领”的旧块：找到就复用它的向量； 找不到就重新嵌入。扫描结束后，旧索引里没有被任何新块认领的条目就是需要删除的内容—— 这自然覆盖了“文件被删”“文件被排除规则排除”“代码被改写”三种情况。

    行号参与哈希，是双刃剑。在文件头部插入几行，后面所有块的行号都会变，于是整文件重嵌入。 好处是“块内容 + 位置”一起变才重建，避免旧内容错位；代价是对自动生成的巨型文件不友好。 这是设计取舍，不是缺陷。

    失败语义：add 全有或全无，update 可回滚

    两个写操作的失败策略不同，因为它们的风险不同：

    • add 失败：删掉知识库记录、chunks、symbols、job，再删向量文件。不留下半成品。
    • update 失败：只删本轮新插入的 chunk，恢复旧状态；向量文件从未被原地修改，旧索引仍可用。
    • 取消：取消与失败区分——取消时恢复原状态（可能是 ready），真失败才置 error。
    • 更新期间：KB 状态是 indexing，检索会跳过它。用可用性换一致性。

    文件监听：两套机制互为保险

    开启 PI_KNOWLEDGE_WATCH 后，每个目录型 KB 会同时跑两套监听： fs.watch(recursive) 负责及时性，每 2 秒一次的全目录快照轮询负责兜底。 两者共享同一个 2 秒防抖槽，所以一次 git checkout 带来的大量变更只会触发一次 update。

    轮询比较的是 mtime + size 快照，并且复用与索引完全一致的扫描/过滤逻辑—— 这保证“监听范围”和“索引范围”不会漂移。代价是每 2 秒一次目录遍历，虽然在 ignore 规则下已经剪掉了大部分。

    健康诊断：100 分制，不加载模型

    knowledge_status 是轻量视图：逐库列出状态、块数、文件数、当前/上一次 job、覆盖率、陈旧/孤儿/卡死/跳过统计； knowledge_doctor 则输出健康分、问题列表和具体动作。两个工具都不需要加载模型， 所以即使嵌入配置坏了，你仍然能诊断“为什么坏了”。

    先说人话

    就像医院体检：不是告诉你“你不太健康”，而是列出“血压高、缺维 D、该去复查”， 并且每一项都对应一个可执行的动作。

    取舍清单：每一个“聪明”，都有账单

    这份源码最值得学的不是某个公式，而是它如何把“代价”写在明面上。

    主要设计选择及其代价。没有一项是免费的。
    选择换来什么付出什么
    零重叠切块更少存储与向量；不会重复召回同一段跨块上下文要靠 adaptive 在检索期补；块边界处可能断章
    hybrid 词法锚定大幅降低低证据语义误召回换了说法的查询可能被整库跳过；所以另开 semantic_hybrid
    本地模型优先零 API 费、代码不出门、离线可用精度与速度不如云端；首次下载 ~32MB；需要 Node 22+ 子进程
    行号进哈希块位置变化能可靠识别文件头插行会导致整文件重嵌入
    更新期间不可检索不会读到半成品大库更新时该 KB 暂时“下线”
    向量按下标对齐 rowid文件格式极简、扫描快、省内存删除必须整文件重建；无逐条校验和，靠不变量约束
    不自动恢复崩溃任务实现简单，状态可预测中断后需人工 remove + 重建；靠 doctor 提示
    显式失败优于静默回退配置错误、模型不匹配、超预算立刻可见首次使用更容易“报错”，需要读文档

    四条设计哲学

    1. 结构优先于固定窗口。先在内容里找天然边界，再考虑 token 预算；只有在没有结构时才退化成字符切分。
    2. 可诊断性是可交付特性。分数怎么来的、任务卡在哪、文件为什么被跳过——都能被查询，而不是只写在日志里。
    3. 进程隔离优于精细释放。面对原生运行时的不确定性，把风险关进子进程，比在主进程里精确管理生命周期更可靠。
    4. 显式失败优于聪明回退。API 失败、维度不匹配、签名过期、向量缺失——全都给出明确信号和下一步动作。
    一个值得注意的细节：搜索时每个 KB 都会各自嵌入一次查询。 模型有缓存，但多 KB 意味着多次 worker 往返或多次 API 计费。 这不是设计目标，而是当前实现的优化空间。

    7. 0.5.3 – 0.5.62026-07 Windows stdio JSONL worker 传输、Node 22+ 发现（含 Codex runtime）、knowledge_configure 持久化、搜索 profile。 宿主没有 IPC 时，嵌入子系统仍然要能工作。
    8. 0.6 – 0.82026-07 – 08 嵌入签名 + 维度元数据、文档批嵌入禁止回退、旧库降级 BM25 + warning、可配置重排器（HF / API / TEI / raw logits）、工具审批分级。 向量空间兼容性必须显式建模，连 base URL 变了都算不兼容。
    9. 0.9 – 0.112026-08 – 10 递归 AST 切块、同父兄弟打包、Bash/C/C++/QML 支持、缺失向量修补、embedding 批量可调、前缀 on/off、semantic_hybrid。 代码检索需要真正的结构信息，而不是正则猜函数边界。
    10. 0.12.02026-10-19 embedding-safe 二次切分（策略版本 2）、无依赖 HTML 结构化、doctor 提示 reindex、单飞模型加载。 “截断不报错”是最隐蔽的数据损失；凡是改变块文本/边界的策略都必须版本化。

    术语表

    术语一句话解释
    RAG先检索资料，再让模型基于资料回答
    Chunk从原始文件切出来的一段可检索文本
    Embedding把文本映射成一串数字（向量），语义近则距离近
    BM25基于词频和逆文档频率的关键词打分算法
    FTS5SQLite 内置的全文检索模块
    Hybrid关键词检索与向量检索的结合
    RRF只看名次的融合方法；本项目保留但未启用
    MMR在相关性和多样性之间取平衡的重排方法
    Reranker对候选做二次打分的模型，通常更慢更准
    AST抽象语法树；代码切块用它找函数/类边界
    Provenance结果的出处与新鲜度信息
    最后一句

    这套系统真正的核心不是“向量数据库”或“BM25”，而是把“检索”拆成一串可解释、可诊断、可回滚的小决定： 切在哪、加什么前缀、什么时候不回答、为什么这条排第一。 模型会换，公式会调，但这套工程方法不会过时。
