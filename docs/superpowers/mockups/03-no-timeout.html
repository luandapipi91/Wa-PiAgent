"不设限" 必须设计好的 3 件事

① 研发回复前，产品进程必须活着
pi-intercom 默认 10 分钟超时是 tool 层的（防呆）。
你的机制：编排内核包装 ask，把超时设为 Infinity。tool 永远 await，直到：
✓ 研发通过 intercom reply 回复
✓ 用户手动替答（编排内核合成一个 reply）
✓ 用户手动取消这次 ask
✓ 产品或研发进程被关闭
② 队列透明：研发同时被多人 ask 怎么办？
不设限意味着可能积压。IntercomMonitor 必须跟踪并可视化每个 agent 的 pending 队列：
• 研发节点上显示 队列: 2 (产品, PM)
• 当前处理的是哪一个（FIFO？还是研发 LLM 自己挑？）
• 每个等待者已等了多久（不是"还剩多久"，是"已等"）
③ 用户必须能随时介入（但不强制）
不设超时 = 不会自动放弃 = 用户必须自己有手段结束/加速。
但这是可选的干预，不是强制的倒计时。永远挂在那等也是合法状态。

需要你确认的设计决策

1. ask 超时 = Infinity ✅ 已确认（你的决策）
2. 队列调度：研发被多人 ask 时，FIFO（先到先处理）还是研发 LLM 自己选（看上下文挑重要的答）？
3. 并发处理：研发可以同时回复多个 ask（maxConcurrency > 1，一个 turn 处理一个，但多个 turn 并行）还是串行（一次一个）？
4. "催一下"按钮：点了之后做什么？给研发插队一条高优先级 steer 消息？还是给用户一个输入框直接打字给研发？
A

FIFO + 串行（推荐，最简单）

研发按 ask 到达顺序处理，一次只处理一个。其他排队等。可预测、可调试。maxConcurrency=1。

B

研发 LLM 自己挑 + 串行

研发看到队列，LLM 决定先答哪个（可能先答简单的）。更智能但不可预测。

C

并行处理（maxConcurrency=N）

研发可同时回复多个 ask，每个开独立 turn。最快但上下文最复杂、最烧 token。
